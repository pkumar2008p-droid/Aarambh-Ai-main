# AARAMBH Follow-up Navigator

AARAMBH is a follow-up coordination prototype with a Flask API, PostgreSQL data store, and React/Vite frontend.

## Architecture

- `backend/`: Flask API, PostgreSQL adapter, encryption/session helpers, risk engine, and model training.
- `backend/schema.sql`: PostgreSQL schema. Run this once before starting the API.
- `frontend/`: React/Vite static frontend. Patient/staff sign-in and the follow-up list use the Flask API.
- `render.yaml`: Render Blueprint with separate API and static frontend services.

Supabase and Supabase Storage are not used. Trained model bundles are stored in PostgreSQL (`ml_models.model_data` / `BYTEA`) so they survive Render redeploys.

## Required environment variables — API service

| Variable | Required | Purpose |
|---|---:|---|
| `DATABASE_URL` | Yes | Render PostgreSQL connection string |
| `DATA_KEY` | Yes | Fernet encryption key for protected patient data |
| `PEPPER` | Yes | High-entropy secret used for HMACs |
| `FRONTEND_ORIGINS` | Yes for split hosting | Exact frontend origin, e.g. `https://aarambh-frontend.onrender.com` |
| `APP_ENV` | Recommended | Set to `production` on Render |
| `COOKIE_SAMESITE` | Recommended | Set to `None` when frontend and API are cross-site; always HTTPS |
| `TWILIO_SID`, `TWILIO_TOKEN`, `TWILIO_FROM` | Optional | Real patient OTP SMS delivery |
| `ANTHROPIC_API_KEY` | Optional | Enables the restricted help chatbot |
| `CLAUDE_MODEL` | Optional | Anthropic model identifier when the chatbot is enabled |
| `HOSPITAL_LAT`, `HOSPITAL_LNG` | Optional | Hospital coordinates for estimated travel distance |

Generate a Fernet key locally (do not commit it):

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Generate a separate HMAC pepper locally:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Never put real `.env` files, database URLs, encryption keys, API keys, Twilio tokens, or patient data in GitHub. `.env.example` files contain placeholders only.

## Required environment variable — frontend static site

Set `VITE_API_BASE_URL` to the full API origin, without a trailing slash, for example:

```text
https://aarambh-ai.onrender.com
```

Set `FRONTEND_ORIGINS` on the API service to the exact frontend origin, for example:

```text
https://aarambh-frontend.onrender.com
```

Because the browser uses a secure HTTP-only cookie across two origins, the API uses credentialed CORS and `SameSite=None; Secure`. Both services must use HTTPS. For custom domains, update both values to the exact origins.

## Render deployment

1. Create a Render PostgreSQL database and copy its **Internal Database URL** into the API service's `DATABASE_URL` environment variable. If the API is not on Render's private network, use the provider's appropriate external connection URL instead.
2. From the repository root, set `DATABASE_URL` to the Render **External Database URL** locally and run `python -m backend.migrate` to apply `backend/schema.sql` once. Do not run the schema against a database containing unrelated tables.
3. For the existing `AARAMBH-AI` Render Web Service, open **Settings → Build & Deploy** and set **Root Directory** to blank (repository root), **Build Command** to `pip install -r requirements.txt`, **Start Command** to `gunicorn backend.app:app --workers 1 --threads 4 --timeout 120`, and **Health Check Path** to `/healthz`. The older service was originally configured with `rootDir: backend`; that setting is incompatible with package-relative imports. The `render.yaml` defines the intended API and static frontend services for a Blueprint-based setup.
4. Add `DATA_KEY`, set `FRONTEND_ORIGINS`, and set frontend `VITE_API_BASE_URL` in the Render dashboard. `PEPPER` is generated by the Blueprint; keep it stable across deploys.
5. Render uses `/healthz` for process liveness so the Web Service can start before schema setup. After migration, check `https://<api-host>/api/health`. A healthy response includes `{"ok":true,"database":"connected"}`. It returns HTTP 503 if PostgreSQL or required application tables are missing.
6. Build the frontend after setting `VITE_API_BASE_URL`; Vite embeds this value at build time, so trigger a new static-site deploy after changing it.

Build/start commands:

```bash
# API (repository root)
pip install -r requirements.txt
gunicorn backend.app:app --workers 1 --threads 4 --timeout 120

# Frontend (frontend directory)
npm ci
npm run build
```

## Create initial staff / optional synthetic demo records

After the schema is installed and the API environment variables are available locally, run from the repository root:

```bash
python -m backend.seed
```

The script creates random staff passwords and prints them once. Save them securely; do not commit them. For synthetic demo patients only, run:

```bash
python -m backend.seed --demo
```

For a fixed OTP on synthetic `is_demo` records, set both `ALLOW_DEMO_OTP=true` and `DEMO_OTP` only in an isolated demonstration environment. Never enable fixed OTPs for real patient accounts. Do not seed demo records into a production database containing real patient information.

## Local development

Create a local `.env` in the repository root with `DATABASE_URL`, `DATA_KEY`, and `PEPPER`. Then:

```bash
pip install -r requirements.txt
python -m backend.app
```

In a second terminal:

```bash
cd frontend
npm ci
npm run dev
```

The Vite dev server proxies `/api` to `http://127.0.0.1:5000`; set `VITE_API_BASE_URL` only when using a separate API host.

## Important limitations

- Existing Supabase records and Storage objects are **not migrated** by this code change. Export and migrate them separately before retiring any old database.
- Patient self-registration is not implemented. Patient records must be provisioned by authorised hospital staff or a controlled data-import process.
- Real OTP delivery requires Twilio credentials. Without them, the API deliberately does not print OTP values into logs.
- The AI risk score is a follow-up coordination aid, not a clinical triage or diagnostic tool. Model retraining needs a sufficient, balanced dataset and should be reviewed before use.
- This project is a software prototype. Complete security, privacy, clinical, and operational review is required before handling real patient data.
